# nRF24L01+

The nRF24L01+ decoder reads the SPI traffic between a host and a Nordic Semiconductor nRF24L01+ 2.4 GHz transceiver: it turns `spi.events` into `nrf24l01.events`, one command per chip select period, with the STATUS register the chip returns, the registers it names and the data it moves. It follows the nRF24L01+ Product Specification v1.0 — chapter 8, the SPI interface and its command set, and chapter 9, the register map — with ACTIVATE from the nRF24L01 Product Specification v2.0, the part before the plus.

| Node      | `Nrf24l01` (`nrf24l01`)                                                               |
| --------- | ------------------------------------------------------------------------------------- |
| Input     | `bus`: `spi.events` version 1                                                         |
| Output    | `events`: `nrf24l01.events` version 1                                                 |
| Requires  | `wordBits` = 8, `bitOrder` = `"msb-first"`, `cs` = true, `mosi` = true, `miso` = true |
| Declares  | nothing                                                                               |
| Configure | nothing                                                                               |

The chip uses SPI mode 0, with CSN as chip select.

## Events

Every event but `unknown` names its operation, `op`, numbered from 1. An operation begins with `command`, ends with `end`, and carries its `data` between them.

| `kind`    | Fields                                                              | Meaning                                                                                                                                                                                                                                    |
| --------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `command` | `op`, `tx`, `command`, `register`, `registerName`, `pipe`, `status` | A command byte the decoder knows; `tx` is the SPI transaction, `status` the STATUS register the chip sent on MISO during the command byte; `register` (and its name) for the register commands, `pipe` for W_ACK_PAYLOAD, `null` otherwise |
| `data`    | `op`, `direction`, `offset`, `bytes`                                | The command's data in bus order, at most 32 bytes: `in` to the chip on MOSI, `out` from the chip on MISO; `offset` counts from the command's first data byte                                                                               |
| `end`     | `op`, `reason`                                                      | `complete`, `incomplete`, `too-long` or `aborted` (below)                                                                                                                                                                                  |
| `unknown` | `tx`, `command`, `status`                                           | A transaction whose command byte names no command, with STATUS; the rest of it is skipped                                                                                                                                                  |

```json
{"kind":"command","op":1,"tx":1,"command":"w-register","register":16,"registerName":"tx-addr","pipe":null,"status":14}
{"kind":"data","op":1,"direction":"in","offset":0,"bytes":[231,231,231,231,231]}
{"kind":"end","op":1,"reason":"complete"}
```

Values are bus data: STATUS, register values and payloads are not interpreted, and a multi-byte register's bytes come as on the bus, least significant byte first.

## Commands

| Command byte | `command`            | Data                                        |
| ------------ | -------------------- | ------------------------------------------- |
| `000A AAAA`  | `r-register`         | out: 1 byte to the register's width         |
| `001A AAAA`  | `w-register`         | in: 1 byte to the register's width          |
| `0110 0001`  | `r-rx-payload`       | out: 1 to 32 bytes                          |
| `1010 0000`  | `w-tx-payload`       | in: 1 to 32 bytes                           |
| `1110 0001`  | `flush-tx`           | none                                        |
| `1110 0010`  | `flush-rx`           | none                                        |
| `1110 0011`  | `reuse-tx-pl`        | none                                        |
| `0110 0000`  | `r-rx-pl-wid`        | out: 1 byte                                 |
| `1010 1PPP`  | `w-ack-payload`      | in: 1 to 32 bytes; PPP is the pipe, 0 to 5  |
| `1011 0000`  | `w-tx-payload-noack` | in: 1 to 32 bytes                           |
| `1111 1111`  | `nop`                | none                                        |
| `0101 0000`  | `activate`           | in: the key `0x73`, which makes it ACTIVATE |

`AAAAA` is the register's address. `0x50` without `0x73` after it, `1010 1110`, `1010 1111` and every byte the table leaves out are `unknown`.

## Registers

`registerName` names the register at `register` after the register map, in kebab-case.

| Address        | `registerName`              | Datasheet name          | Bytes |
| -------------- | --------------------------- | ----------------------- | ----- |
| `0x00`         | `config`                    | CONFIG                  | 1     |
| `0x01`         | `en-aa`                     | EN_AA                   | 1     |
| `0x02`         | `en-rxaddr`                 | EN_RXADDR               | 1     |
| `0x03`         | `setup-aw`                  | SETUP_AW                | 1     |
| `0x04`         | `setup-retr`                | SETUP_RETR              | 1     |
| `0x05`         | `rf-ch`                     | RF_CH                   | 1     |
| `0x06`         | `rf-setup`                  | RF_SETUP                | 1     |
| `0x07`         | `status`                    | STATUS                  | 1     |
| `0x08`         | `observe-tx`                | OBSERVE_TX              | 1     |
| `0x09`         | `rpd`                       | RPD                     | 1     |
| `0x0A`, `0x0B` | `rx-addr-p0`, `rx-addr-p1`  | RX_ADDR_P0, RX_ADDR_P1  | 1–5   |
| `0x0C`–`0x0F`  | `rx-addr-p2` … `rx-addr-p5` | RX_ADDR_P2 … RX_ADDR_P5 | 1     |
| `0x10`         | `tx-addr`                   | TX_ADDR                 | 1–5   |
| `0x11`–`0x16`  | `rx-pw-p0` … `rx-pw-p5`     | RX_PW_P0 … RX_PW_P5     | 1     |
| `0x17`         | `fifo-status`               | FIFO_STATUS             | 1     |
| `0x1C`         | `dynpd`                     | DYNPD                   | 1     |
| `0x1D`         | `feature`                   | FEATURE                 | 1     |

The address registers take as many of their five bytes as SETUP_AW sets, 3 to 5. The map leaves out `0x18` to `0x1B`, `0x1E` and `0x1F`: their `registerName` is `null`, and the decoder takes up to five bytes for them.

## Decoding rules

- **One command per transaction.** Its first word is the command byte on MOSI, with STATUS on MISO; the words after it are the command's data, on MOSI for the commands that write and on MISO for those that read. An unknown command byte is reported as `unknown` and the rest of its transaction is skipped. `0x50` is decided by the next byte: ACTIVATE with `0x73`, `unknown` with anything else or with the release.
- **Ends.** The operation ends `complete` when chip select is released after the command's fewest bytes — none for the commands without data, one for the others — and `incomplete` before them: a register or payload command without a data byte. It ends `too-long` at the first byte past the most it takes; the rest of the transaction is skipped. A gap or the end of the samples during a command ends it `aborted`, after the data read so far; the gap or the end is then passed on.
- **Data** goes out in one batch of at most 32 bytes: as soon as the command has the most bytes it takes — the register's width, 32 for a payload, one for R_RX_PL_WID — or when its end decides it, so that a register write shows up before chip select is released.
- **Partial transactions.** A transaction already under way when the samples begin or after a gap is skipped: its first word is not the command byte, and its words may not be aligned on bytes.

## Placement

| Event                            | Span                                                    | Settled                                                                 |
| -------------------------------- | ------------------------------------------------------- | ----------------------------------------------------------------------- |
| `command`, `unknown`             | chip select's assertion through the command byte's word | the command byte's last bit; for `0x50`, the next byte's or the release |
| `data` (the most bytes)          | the words of the batch                                  | the last byte's last bit                                                |
| `data` (flushed by an end)       | the words of the batch                                  | the end that decided it                                                 |
| `end` (`complete`, `incomplete`) | chip select's release                                   | the release                                                             |
| `end` (`too-long`)               | the first byte too many                                 | its last bit                                                            |
| `end` (`aborted`)                | empty, at the cut                                       | the gap's start or the end of the samples                               |

The events of the stream settle in order, and they are the same however the samples are cut into blocks and however the reader pauses.

## Limits

- The decoder does not follow the chip's configuration — SETUP_AW, the static payload widths, dynamic payloads — so it takes up to five address bytes and up to 32 payload bytes whatever the chip is set to.
- It does not judge whether the chip accepted a command: W_REGISTER is only executed in power down and standby, payload writes need room in the FIFO.
- Progress is passed on between transactions only.
