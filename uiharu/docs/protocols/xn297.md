# XN297

`xn297` is a byte-SPI overlay for the original Panchip XN297. It identifies commands and registers, streams TX/RX payload bytes, and reports selected digital configuration and returned status fields. It validates the 64-byte payload bound and the distinct five-byte DEMOD_CAL, seven-byte RF_CAL and five-byte BB_CAL register widths. ACTIVATE requires the observed 0x73 key.

This is separate from the existing nRF24L01+ profile, whose 32-byte payload limit and register map do not describe these calibration registers. XN297L and other clone maps, analog calibration interpretation and over-air scrambling are outside this profile. No whole payload is buffered. Gaps abort partial transactions; already emitted observations retain their provenance.

Reference: [Panchip original 2012 XN297 specification](https://deviationtx.com/media/kunena/attachments/1511/xn297datasheet.pdf), sections 7.3/7.6 and tables 6/8. The compiled/interpreted regression independently exercises seven calibration bytes, 64 payload bytes, an overlong payload, status fields and an invalid activation key.

The `model` option selects `original` (2012) or `xn297l` (manufacturer V4.6). Original calibration widths are 19h five bytes, 1Eh seven bytes and 1Fh five bytes. XN297L widths are 19h one byte, 1Ah six bytes, 1Bh three bytes, 1Eh three bytes and 1Fh one byte, as specified in the [Panchip XN297L manufacturer document](https://datasheet.lcsc.com/datasheet/pdf/45bf1129bd364889783cdc4ddfb5f751.pdf).

The pinned DSView `nrf24l01` option `chip=xn297` matches the XN297L map at 19h/1Ah/1Bh/1Eh, but treats 1Fh as five bytes. The primary XN297L table explicitly defines BB_CAL as bits 7:0, so this implementation accepts one byte. Import selects `model=xn297l` with a profile note and preserves the raw original configuration; it does not silently pretend the maps are identical. Register operands remain raw bytes where no supported digital subfield is decoded.
