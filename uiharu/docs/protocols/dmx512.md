# DMX512

The `dmx512` decoder reads the packets of a DMX512-A line from the characters and breaks of a UART stream and emits them as `dmx512.events`. It follows ANSI E1.11, Entertainment Technology — USITT DMX512-A: data at 250 kbit/s over EIA-485, every slot a character of a start bit, eight data bits sent least significant first, no parity and two stop bits; a packet is a break (space for at least 92 µs from a transmitter, 88 µs at a receiver), a mark after break (at least 12 µs, 8 µs at a receiver), the start code slot (0 for dimmer data, other codes for other kinds of data) and up to 512 data slots.

Packets are framed by breaks, so the decoder is stacked on the [UART decoder](uart.md), configured for the DMX512 character format by `Dmx512::uart_config`:

```rust
let uart = graph.add(Uart::new(Dmx512::uart_config(0))?);
let dmx = graph.add(Dmx512::new());
graph.connect(logic.samples, Uart::input(uart))?;
graph.connect(Uart::events(uart), Dmx512::input(dmx))?;
let packets = graph.expose("dmx", Dmx512::events(dmx))?;
```

`uart_config(line)` reads the line on channel `line` with mark high, as the receiver's output or the transmitter's input of an EIA-485 transceiver carries it; a probe on the inverting side of the pair needs the UART's `inverted` set as well. The decoder takes no configuration.

## Requirements

The input port `uart` requires of the UART stream:

| Property   | Requirement     |
| ---------- | --------------- |
| `baud`     | `= 250000`      |
| `dataBits` | `= 8`           |
| `parity`   | `= "none"`      |
| `stopBits` | `= "two"`       |
| `bitOrder` | `= "lsb-first"` |

The UART's own input requires a source of at least 500 kHz (two samples per bit); 1 MHz or more is advisable. A connection that does not meet the requirements is refused, for example `dmx512#1.uart requires baud = 250000 of uart#0.events, which declares 115200`.

## The stream: `dmx512.events` v1

Packets are numbered from 1. A packet is a `packet-begin`, its `start-code`, its data `slots` and a `packet-end`, all carrying the packet's id. Slots are numbered as E1.11 numbers them: slot 0 is the start code, slots 1 to 512 carry the data, and a fixture at DMX address _a_ reads data slot _a_.

| Kind           | Fields                            | Meaning                                                                                                                                                                   |
| -------------- | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `packet-begin` | `packet`, `breakTicks: u64`       | A break began a packet; `breakTicks` is how long the line was held at space                                                                                               |
| `start-code`   | `packet`, `code: u8`              | The first slot after the break: 0 for dimmer data; other codes (such as `0xCC` for RDM, `0x17` for text) carry other data                                                 |
| `slots`        | `packet`, `offset: u32`, `values` | Data slots in order, at most 32 per event; `offset` counts the data slots before `values[0]`, which is slot `offset + 1`                                                  |
| `packet-end`   | `packet`, `slots: u32`, `reason`  | The packet ended: `break` when the next break began, `aborted` when a gap or the end of the stream came first; `slots` counts its data slots, the start code not included |
| `error`        | `packet`, `slot: u32`             | The character of this slot had a framing error, a stop bit read at space; its value is reported all the same, in the `start-code` or in the `slots` event just before     |

```json
{"kind":"packet-begin","packet":1,"breakTicks":176}
{"kind":"start-code","packet":1,"code":0}
{"kind":"slots","packet":1,"offset":0,"values":[255,128,0,0,40]}
{"kind":"error","packet":1,"slot":5}
{"kind":"packet-end","packet":1,"slots":5,"reason":"break"}
```

| Event                  | Span                                                            | Settled                                      |
| ---------------------- | --------------------------------------------------------------- | -------------------------------------------- |
| `packet-begin`         | the break, from its falling edge to the first tick back at mark | that tick, where the UART reported the break |
| `start-code`           | the start code's character                                      | its last stop bit's sample point             |
| `slots` (a full batch) | the characters of the batch                                     | the last one's last stop bit's sample point  |
| `slots` (the rest)     | the characters of the batch                                     | the end, or the error, that sent it out      |
| `error`                | the character                                                   | its last stop bit's sample point             |
| `packet-end` (break)   | empty, at the falling edge of the break that ends it            | where that break was reported                |
| `packet-end` (aborted) | empty, at the gap's start or the end of the stream              | that tick                                    |

The timing E1.11 sets is not checked, but can be read from the spans: the break's length is `breakTicks`; the mark after break runs from the end of the `packet-begin` span to the start of the `start-code` span; a time between slots shows as room between the characters of a batch; the mark before break runs from the end of a packet's last character to its `packet-end`. The source's `rateHz` turns ticks into time.

The output port `events` declares no properties.

## Decoding rules

- Every break the UART stream reports begins a packet, whatever its length, which `breakTicks` reports: a short break shows rather than being judged. The UART calls a break a space held through a whole character, stop bits included (about 44 µs at 250 kbit/s); a shorter space reads as a character instead, usually with a framing error. A packet under way when a break begins ends there, `break`.
- The first character after the break is the start code, every later one a data slot, reported as the line carried it. Data values go out in batches of at most 32: when a batch is full, when one of its slots had a framing error, or when the packet ends.
- A character with a framing error keeps its value, and an `error` naming its slot follows the `start-code` or the batch that holds it.
- Characters before the first break, and after a gap until the next break, belong to no packet and are dropped: a start code cannot be told from data there.
- A gap or the end of the stream ends the packet under way `aborted`, at the gap's start or the end; the values it holds go out first.
- A packet is ended by the next break or by the stream, nothing else: E1.11 lets the line idle for up to a second between slots and before the next break, and ending a packet on a timeout is out of scope.
- Progress is passed on, held back to the first slot of a batch not yet sent.

## Limits

- No timeout ends a packet: the last packet of a capture ends `aborted`.
- The break, the mark after break and the times between slots are reported, not checked against E1.11's minimums and maximums.
- Start codes are not interpreted: the slots of RDM and other alternate start codes are reported as plain data.
- Packets with more than 512 data slots are reported as the line carried them, slot numbers past 512 included.

## Timing and individual slots

The exact `dmx512.events@1` JSON contract is declared in
`dsl/contracts/dmx512.ts`; the native producer emits those generated types.
Packet IDs are scalar `u64` values; `Dmx512EventExt` retains the packet lookup
helper.

For receiver timing checks, individual slot events, zero-dimmer filtering and
alternate-start-code identification, use [dmx512-analysis](dmx512-analysis.md)
directly above the UART. This preserves the individual character timestamps
that cannot be reconstructed from the native transport's batches.
