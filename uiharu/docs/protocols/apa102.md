# APA102

The `apa102` decoder reads the frames a controller clocks into a chain of APA102 or SK9822 LEDs from the words of an SPI stream and emits them as `apa102.events`. It follows the APA102 and APA102C datasheets (Shiji Lighting) and the SK9822 datasheet (Shenzhen Normand Electronic): two wires, clock and data, the data taken on the clock's rising edge, most significant bit first — SPI without chip select. A frame is a start frame of 32 zero bits, one 32-bit LED frame per LED — the bits `111`, five bits of global brightness, then a blue, a green and a red byte — and an end frame of at least half as many bits as there are LEDs: ones on the APA102; on the SK9822 zeros, after a reset frame of 32 zero bits before the next start frame. Each LED keeps the first LED frame it receives after a start frame and passes the rest on.

The decoder is stacked on the [SPI decoder](spi.md), with or without a chip select line:

```rust
let spi = graph.add(Spi::new(SpiConfig {
    clk: 0,
    cs: None,
    mosi: Some(1),
    miso: None,
    ..SpiConfig::default()
})?);
let leds = graph.add(Apa102::new());
graph.connect(logic.samples, Spi::input(spi))?;
graph.connect(Spi::events(spi), Apa102::input(leds))?;
let frames = graph.expose("leds", Apa102::events(leds))?;
```

The parts take data on the rising edge of the clock, so the SPI decoder reads them in mode 0 or 3. The decoder takes no configuration.

## Requirements

The input port `bus` requires of the SPI stream:

| Property   | Requirement     |
| ---------- | --------------- |
| `wordBits` | `= 8`           |
| `bitOrder` | `= "msb-first"` |
| `mosi`     | `= true`        |

Chip select and MISO may be connected or not; `cs` decides how the stream is read (see below). A connection that does not meet the requirements is refused, for example `apa102#1.bus requires wordBits = 8 of spi#0.events, which declares 4`.

## The stream: `apa102.events` v1

Frames are numbered from 1. A frame is a `frame-begin`, one `led` per LED frame, and a `frame-end`, all carrying the frame's id.

| Kind          | Fields                                                      | Meaning                                                                                                                                       |
| ------------- | ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `frame-begin` | `frame`                                                     | A start frame began a frame                                                                                                                   |
| `led`         | `frame`, `index: u32`, `brightness`, `blue`, `green`, `red` | One LED frame: `index` counts from 0 for the first LED the data reaches; `brightness` is the five bits of global brightness, 0 to 31, as sent |
| `frame-end`   | `frame`, `leds: u32`, `endBits: u32`, `reason`              | The frame ended: `leds` LED frames, then `endBits` bits — the end frame, and an SK9822's reset frame — up to its end, for the `reason` below  |
| `error`       | `frame`, `reason: "header"`                                 | The first byte after the start frame lacks the `111` bits; the frame has no LED frames                                                        |

| Reason       | When                                                                                        |
| ------------ | ------------------------------------------------------------------------------------------- |
| `next-frame` | the next frame's start frame came                                                           |
| `release`    | chip select was released: on a bus with chip select every transaction is read on its own    |
| `aborted`    | a gap or the end of the stream came, or the transaction was cut off, before the frame ended |

```json
{"kind":"frame-begin","frame":1}
{"kind":"led","frame":1,"index":0,"brightness":31,"blue":16,"green":32,"red":48}
{"kind":"led","frame":1,"index":1,"brightness":1,"blue":0,"green":128,"red":0}
{"kind":"frame-end","frame":1,"leds":2,"endBits":8,"reason":"next-frame"}
```

`endBits` lets a reader check the end frame against the rule of at least half as many bits as LEDs; on an SK9822 chain it counts the reset frame too.

| Event         | Span                                                                                                                                          | Settled                                                                      |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `frame-begin` | the start frame's four bytes                                                                                                                  | the byte after it, which decided it                                          |
| `led`         | its four bytes                                                                                                                                | its last byte, or the byte or end that showed no start frame reaches into it |
| `error`       | the byte                                                                                                                                      | the byte                                                                     |
| `frame-end`   | its end bits: up to the next start frame, through chip select's release, or to the last of them when aborted; empty there when there are none | the byte after the next start frame, the release, the gap's start or the end |

A byte spans its first bit's sampling edge to its last bit's sampling edge + 1, as the SPI stream has it. The output port `events` declares no properties.

## Decoding rules

- A start frame is four zero bytes: the last four zero bytes before a byte that is not zero, so that a run of zeros longer than four — an end frame or a reset frame of zeros, followed by the next start frame — is told apart when it ends. That byte begins the frame as its first LED frame's first byte.
- A byte with its top three bits `111` at the start of an LED frame begins one, which takes it and the three bytes after it.
- LED frames follow one another until a byte at the start of an LED frame lacks the `111` bits: from there on the bytes are the end of the frame, counted in `endBits` and not interpreted, up to the next start frame. When the very first byte after a start frame lacks the bits, the frame reports an `error` and has no LED frames.
- An LED frame whose last bytes are zero can hold the beginning of the next start frame, as when an end frame of one or two bytes of ones is followed by the next start frame. It is reported once it is known not to: when a byte that is not zero comes before four zero bytes have followed it, when four have, or when the frame ends otherwise. When the start frame does reach into it, it is no LED frame, and its bytes before the start frame are end bits.
- With chip select (`cs = true` on the SPI stream) each transaction is read on its own, from a search for a start frame, and a frame under way when chip select is released ends `release`; the bytes after its last LED frame, an LED frame cut short among them, are its end bits. Without chip select the stream is read as one, and a frame ends when the next one's start frame is found, `next-frame`.
- A gap, the end of the stream or a transaction cut off ends the frame under way `aborted`, its bytes after the last LED frame counted the same way.
- Bytes before the first start frame — of the stream, after a gap, or in a transaction — belong to no frame: a frame under way when the samples begin yields nothing until a start frame.
- Progress is passed on, held back to the first byte of whatever is still to be reported: an LED frame, the end bits, or zero bytes that may become a start frame.

## Limits

- The end frame of the APA102 datasheet, 32 one bits, has the shape of an LED frame — brightness 31, full white — and is reported as one: only a reader that knows how long the chain is can tell the two apart. End frames shorter than 32 bits, or of zeros, are counted as end bits.
- The bytes are the SPI decoder's words. Without chip select they line up with the bytes the controller sent only if the samples begin, and resume after a gap, while the clock is idle between two bytes; otherwise every later word is shifted and nothing after is read right. With chip select every transaction lines them up anew.
- A frame split over several transactions is not joined: read such a bus without chip select.
- The brightness is reported as sent, not applied to the colours, and the chain's output (the clock and data an LED passes on) is not decoded.
- When the LEDs latch the data they received, which the SK9822's reset frame is there for, is not modelled.
